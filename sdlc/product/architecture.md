# Architecture: MouldTrack
Status: approved · Updated: 2026-11-25 (05, 06, 07, dev-reset, 08, explicit-grants, r1-release-prep)

## Stack
- **App:** Expo (React Native) + TypeScript + Expo Router, one codebase for Android (supervisors) and web (admins and Super Admin, via react-native-web). Android first; iOS later. Exact Expo SDK version pinned in 01.
- **Backend:** Supabase. Postgres with row-level security (RLS) for tenant isolation, Auth (phone number + password, see Identity), Storage for photos, Postgres functions (RPC) for workflow transitions so the rules and idempotency sit on the server. **Edge Functions** (Deno) only for operations that need the service role (Auth admin calls); they stay thin and call service-only SQL functions that hold every rule (02).
- **Builds/deploy:** EAS Build (Android, distributable builds only) + EAS Update channels `development` / `preview` (staging) / `production`. Web: `expo export` with `web.output: "static"` on **EAS Hosting** (Vercel Hobby forbids commercial use). CI/nightly Android APKs are built on the GitHub runner (`scripts/build-android-ci.sh`), not EAS (Free ≈ 15 Android builds/month).
- **Quality:** ESLint · `tsc` · Jest + React Native Testing Library (unit) · pgTAP via `supabase test db` (DB/RLS) · Playwright against the web build (e2e) · Maestro on an Android emulator (mobile e2e) · GitHub Actions.
- **Monitoring:** Sentry Free/Developer (errors only: no tracing, no replay, `sendDefaultPii: false`; 1 user, ~5k errors/month), Supabase logs.

## Core entities
Tenant (+ plan label Trial/Active) → Site (one per tenant in R1) → Line (optional grouping) → Machine · Product · TargetVersion (machine × product, pieces per shift, effective-dated, append-only; = the PRD's MachineProductBenchmark; per-shift overrides in 05) · Shift (start/end time; occurrence = shift + start date) · ShiftAssignment = `assignment_version` (recurring plan, effective-dated) + `assignment_cover` (one occurrence) · TargetOverrideVersion (machine × product × shift) · ProductionReading (append-only, corrections supersede) · ProductionSummary (versioned calculation) · CavityVersion (machine × product, effective-dated, append-only) · machine counter settings (unit pieces|shots, optional maximum) · IssueCategory · MachineIssue → IssueAction, IssueOwnershipHistory · Handover (`handover_setting`, `handover_session`, `issue_acknowledgement`, `handover_declaration`, `handover_exception`, `handover_note`; 08) · Attachment (two-phase upload, Storage bucket `attachments`) · AuditEvent · User/Membership (user × tenant × role).

## Auth & permissions model
- Roles: `platform_admin`, `unit_admin`, `supervisor` (`maintenance` reserved).
- Every tenant-owned row carries `tenant_id`. RLS checks it against the caller's membership. A supervisor additionally sees only assigned machines and shifts.
- **Platform Super Admin (03)** = a row in `platform_admin` (not a tenant member); same phone + password sign-in, routed to the web Console. One phone per person across `membership` and `platform_admin` (`app.phone_claim`, kept by triggers). SAs register/edit/suspend/activate tenants (plan label Trial/Active is a label only; status Suspended blocks access, sessions kept), create and reset **Unit Admins only**, and manage other SAs (no self-deactivate; never the last active SA). Writes via the `platform` Edge Function → `app.pa_*` via `public.psvc_*` wrappers (service_role only).
- **SA data boundary:** SAs read `tenant` rows and only what `public.pa_*` read functions expose (tenant summaries with counts, a tenant's UAs with masked phones, the platform audit). No RLS path to membership, tenant users' audit rows or any tenant-owned table; `pm_*`/user-admin paths deny SAs (audited as platform events). Test 022 discovers every table/view with `tenant_id` and fails unless it has fixture rows, the UA control sees them and the SA sees none; it also discovers every client-callable write RPC and asserts SAs are denied. **Extension point:** a feature adding a tenant-owned table adds its fixture rows to 022's fixture block (additions only). Storage objects have no `tenant_id`, so 06 needs its own "SA reads 0 objects" test. Operational-data access grants remain future.
- **First SA per environment:** `platform-setup` Edge Function (no JWT) needs secret `PLATFORM_SETUP_TOKEN` (≥ 32 characters, generated with `openssl rand -hex 32`; the public local literal is refused off localhost). It refuses once a Super Admin has completed their first password change; until then a setup-created SA whose temporary password expired can be re-issued (audited). With no token configured it refuses without touching the DB. Runbook: `sdlc/releases/README.md`. dev uses fixture SAs (`fixtures-reset`); staging and prod use the runbook (staging with a canonical fixture phone such as `…00098` and an invented name, never a real person).
- Denied cross-tenant access attempts on RPC paths are recorded as audit events (PRD AC-22).
- Helpers `app.current_tenant_id()` / `app.current_role()` return null unless the caller's membership is active, the tenant is active **and** `must_change_password = false`; every RLS policy builds on them, so a user with a temporary password sees no tenant data.
- Unit Admins manage people (create UA/SUP, edit, role change, deactivate/reactivate, reset password) only via the `user-admin` Edge Function. Guards: no self-deactivate/demote/reset; a tenant always keeps ≥ 1 active UA (tenant row lock). The last UA's password is reset by the Super Admin (03). Deactivation = membership `inactive` + Auth ban. Accounts are admin-created only (public sign-up disabled).
- **Audit actions** are registered in `app.audit_action` (each feature inserts its own; unknown actions fail the CHECK with 23514). SA actions carry `actor_role = 'platform_admin'`; tenant-scoped when they act on a tenant (visible to that tenant's UAs), `tenant_id null` otherwise.
- **Denials are returned, not raised** in service SQL functions: an authorisation denial commits an `access.denied` audit row and returns `{ok:false, code}`; validation/duplicate/guard errors raise P0001 (nothing to audit). Later features use the same pattern and `app.audit_denied`.

## Cross-cutting rules
- **Tenant-owned child tables use composite `(tenant_id, id)` foreign keys** so a row can never reference another tenant's parent (04 pattern).
- **Effective-dated config is append-only and never backdated** (e.g. `target_version`): changes add versions from a plant date ≥ today; reads go through functions (`app.target_for`), which skip the tenant check only for `service_role`. A site's timezone is locked once targets exist (it defines what stored dates mean).
- **Shifts (05):** a shift occurrence = (shift, plant date it starts); window = [start, end) in the site timezone, overnight when end < start; `app.shift_window` / `app.current_occurrences` are the only window maths. Ownership resolves **cover > plan > unassigned** via `app.machine_owner(machine, shift, date)`; plan changes start at the first occurrence that hasn't started (started ones change only by cover) and supersede later scheduled changes. `app.machine_owner_now` = owner of the first **assigned** running occurrence. Effective target = per-shift override > base target (`app.effective_target`). Supervisors read planning data only through resolved functions (`my_shift`), never raw tables. The site timezone is locked once targets **or any shift data** exist.
- **Issues (07):** current-state row (`machine_issue`) changed only by `iss_*` RPCs; append-only `issue_action` and `issue_ownership_history` (source `report|reassign|verification_rejected|handover`). Low/Medium close on resolve; High/Critical are verified by the supervisor who owns the machine in an occurrence started after the resolve (never the resolver); a UA verifies only when no other supervisor is eligible (`app.issue_can_verify`, ≤ 60 days ahead). `machine_stopped` ⇒ Critical (CHECK + RPC). UA alerts = open High/Critical, stopped first; Home shows ≤ 5 + "View all alerts"; refresh on focus + 60 s polling (no push until notifications).
- **Readings (06):** `production_reading` rows (kind opening|closing) are never changed: a correction is a new row with `supersedes_id` + reason; the current reading of a kind is the one nothing supersedes, and a machine-occurrence has at most one original per kind (unique index). Flags are stored at insert and never recomputed: `late` (submitted > 30 min after the boundary: opening = start, closing = end), `early` (closing only, submitted > 30 min before the end), `entered_by_ua`; a correction carries the `late` and `early` flags of the original submission, while `entered_by_ua` reflects who submitted the correction. Windows: opening from start − 30 min to **end + 12 h** (late is accepted and flagged, owner and Unit Admin alike); closing needs a current opening and is allowed until end + 12 h. Who: the occurrence's owner (`app.machine_owner`) or a Unit Admin (on behalf); a supervisor corrects until the next occurrence of the shift starts, a Unit Admin any time. Writes are `rd_opening|rd_closing|rd_correct|rd_set_machine_counter|rd_set_cavities|rd_end_cavities|rd_attachment_begin|rd_attachment_commit` (authorise through `app._rd_authorise`, which callers without a membership route via `app._pm_authorise` so 022's static check holds). **Counter semantics:** a machine counts `pieces` or `shots`; the unit is locked once any reading exists (`counter_unit_locked`); `counter_max` is optional and only then is a closing below the opening a **Rollover** (movement = max + 1 − opening + closing), otherwise movement is null and the row is **Needs review** (never guessed). Pieces = shots × `app.cavities_for(machine, product, date)` (1 when unset, effective-dated, "end means end"). The counter maximum in force is stored on each closing (`counter_max`, carried through corrections) and the summary rolls over from that stored value, so a later change of the maximum never rewrites history. **Summary:** `app._rd_compute_summary` appends one `production_summary` row in the closing/correction transaction (`calc_version = 1`, snapshot of product, unit, cavities, maximum, readings, effective target, good, reject; derived movement, unaccounted, attainment = good ÷ target; flags rollover, needs_review, over_reported, late_opening, late_closing, early_closing, entered_by_ua); the latest row is current, older ones stay, and a rule change adds `calc_version = 2` rows without rewriting. Reads: `reading_state` (the caller's machines, occurrences from start − 30 min to end + 12 h), `reading_detail` (history, photos, summary, `default_product_id`, `allowed`), `today_board` (Unit Admin; per shift the latest started and the previous occurrence, assigned machines only, assumed targets reported separately from `totals`); the default product follows occurrence order over current openings. **Capture metric:** `app.reading_capture(tenant, from, to)` (app-only; 09 wraps it) counts assigned machine-occurrences whose end + 30 min has passed, on time = both readings current, neither Late nor Early. Reading photos reuse 07's attachments with entity `production_reading` (path `tenant/<tenant>/reading/<reading>/<attachment>.<ext>`, visible to the owner and Unit Admins, only on a current reading, at most 3 ready, re-checked at commit); `app_policy.can_see_attachment` gained an additive branch that calls `app._rd_can_see_reading`. `app._rd_window` and the three inline owner resolutions (cover > plan in `reading_state_at`, `today_board_at`, `reading_capture_at`) are copies of 05's `app.shift_window` / `app.machine_owner_src`, kept for set-based queries and pinned to the originals by 053 (line 152 region). Photos are allowed only while the caller could still correct the reading (the `rd_correct` window and role rule, checked at begin and at commit). A supervisor's late closing on a shift longer than 12 h can fall outside the supervisor's correction window (the next occurrence of that shift has already started); only a Unit Admin can correct it then. 022's test 30 and its siblings read `pa_audit` pages 0..9 (bounded) so adding client RPCs cannot overflow one page of 50.
- **Handover (08):** at the start of an occurrence O each supervisor S must answer every **inherited issue** (status Open / In progress / Resolved-awaiting-verification, reported before S's **handover start**, on a machine S owns in O by `app.machine_owner`: cover > plan) and then **declare**; only then does `rd_opening` accept S's opening. Handover start = O's start, or the cover time when S got the machine by a cover recorded after O started (`since`). Six tables, all append-only (revoked UPDATE/DELETE + triggers) except `handover_setting` (changed only by `ho_set_overdue`): `handover_setting` (tenant pk, `overdue_minutes` 15..480 default 60, `required`), `handover_session` (snapshot of the overdue minutes in force at S's first interaction of any kind with O: checklist read, acknowledge, refuse, declare or the `rd_opening` gate check; the fallback to the tenant's current setting applies only to an occurrence with no interaction, which is `no_declaration` anyway), `issue_acknowledgement` (`acknowledged|refused` + remark/reason), `handover_declaration`, `handover_exception` (UA decision: reason, owner, `kept`), `handover_note` (outgoing note, 1-300). RLS: Unit Admin read of own tenant only; supervisors read through `handover_checklist()` (items grouped by machine with state, previous owner, last 3 actions, latest note, `allowed_actions`, and a non-blocking "Verify this fix" list from `app.issue_can_verify`). Writes: `ho_acknowledge|ho_refuse|ho_declare|ho_add_note|ho_exception|ho_set_overdue` (authorise through `app._ho_authorise`, a copy of `_pm_authorise` admitting supervisors and Unit Admins; non-members route via `_pm_authorise`; another supervisor, a Super Admin or another tenant = audited denial). Acknowledge makes S the accountable owner (07 ownership history, source `handover`, no row if S already owns it); refuse escalates through 07's escalate path with the owner unchanged and leaves an exception pending until a UA records `ho_exception` (another active supervisor, or the current owner = keep). A declaration is valid for (S, O) when made at or after S's latest handover start; a later cover makes it stale (it stays in history, S declares again). Windows: acknowledge / refuse / declare from start - 30 min to **end + 12 h** (aligned with 06's late-opening window); notes from start to end + 2 h. Reads: `handover_checklist()` (supervisor), `handover_alerts()` (Unit Admin: refusals waiting for an exception oldest first, acknowledgements past their deadline; each bounded to 50 with totals; Home shows 5 + "Show all"). Deadline = handover start + the overdue minutes snapshotted in `handover_session`. A cover that gives a machine to the supervisor who already owned it just before it (previous cover, else the plan) is a no-op: it sets no `since` and cannot make a declaration stale; a repeated cover to one new supervisor keeps the first cover's time (08 step 8b, `app._ho_owners`). `app._ho_owners` is a set-based copy of `app.machine_owner` / `app.shift_window` pinned to the originals by pgTAP 061 (same pattern as 06's `_rd_window`). **Handover compliance = product metric 2:** `app.handover_compliance(tenant, from, to)` (app-only; 09 wraps it) returns, per (S, O) for occurrences that have ended, compliant = declared by the deadline and every inherited issue answered by its deadline (acknowledged, or refused with an exception recorded); reasons `no_declaration | late | exception_missing`; overdue acknowledgements counted separately; an issue closed before its deadline without an answer drops out; unassigned machine-occurrences are excluded. **The one read that writes:** `handover_checklist_at` inserts the `handover_session` snapshot on the first read of an occurrence, so it is volatile (not STABLE) and clients call it through `rpc` (POST), never a GET; `handover_session` rows are the only writes made by a read function.
- **Cross-feature gate rule (08):** a feature that must change an earlier feature's RPC does so by an **additive `create or replace`** in its own migration (08 redefines `public.rd_opening` as 06's body plus one guard `handover_pending`, and `app.pa_tenant_create` as 03's body plus the `handover_setting` row; `issue_action_type_check` is widened the same way). The earlier migrations stay untouched, the earlier features' tests are not edited, and the new behaviour must be switched off for every state those tests create: the 08 gate applies only to tenants with `handover_setting.required = true`.
- **Handover enforcement (D1):** tenants registered through the Console get `handover_setting.required = true` in the same transaction (`app.pa_tenant_create`); the migration backfills `required = true` for every tenant that exists when it runs; tenants inserted directly (pgTAP fixtures, `seed.sql`, `fixtures-reset`) have no row and are not gated, except the fixture tenant `e2e org H` and the dev demo tenant, which are enforced on purpose. There is no RPC or screen that switches enforcement off in R1. Hosted check 10 (nightly `hosted-checks`) fails when a tenant other than the ungated e2e fixtures (A, B, S, U) lacks `required = true`. **Dev backfill note:** after `deploy-dev` applies the migration, the backfill makes dev's org A, B and U enforced until the next dev reset (which rebuilds dev from the migration files and fixtures, where they are not); a hosted proof or nightly that runs between deploy and reset sees them gated.
- **Workflow screens are server-driven:** read functions return `allowed_actions` computed by the same helpers the RPCs use; the client renders only those.
- **Public read functions never accept a client-supplied time** (they use `now()`; logic lives in `app.*_at(p_at)` helpers that tests call). Any date series inside a function is bounded.
- **Explicit Data API grants (chore/explicit-grants):** new Supabase projects no longer grant `anon`/`authenticated`/`service_role` on new `public` objects implicitly (changelog 45329; older projects such as dev keep the old default privileges). **Every migration that creates a table, view, sequence or function states its grants** (and keeps the append-only revokes and the `app`/`app_policy` rules). `20261124900000_explicit_grants.sql` states every grant earlier migrations got implicitly (exact parity with the old-defaults set, idempotent). `supabase/config.toml` sets `[api] auto_expose_new_tables = false`, so local and PR-CI stacks behave like a new project. **Extension point:** `supabase/tests/070_privilege_contract.test.sql` asserts the privilege set of schemas `public`, `app`, `app_policy` for anon/authenticated/service_role/PUBLIC equals an embedded expected list, in both directions (missing grant or extra grant, e.g. UPDATE on an append-only table, fails); a feature adding an object adds its lines to that list (additions only). `scripts/privilege-snapshot.sql` prints the live set.
- **Client-callable write RPCs** (`public.pm_*` pattern; 05 = `sh_*`, 07 = `iss_*`, 06 = `rd_*` because earlier tests pin per-prefix counts): security definer, empty search_path, **every new one authorises via `app._pm_authorise`** (or `_ua_authorise`) — 022 fails otherwise — (same rules as `current_tenant_id`/`current_role`; SAs denied as platform events), D13 denials, request id tied to its RPC (reuse across RPCs → `validation`). `app._rd_authorise` (06) is a copy of `app._pm_authorise` that admits supervisors as well as Unit Admins, the same pattern as 07's `_iss_authorise`; callers without a membership still route through `_pm_authorise` so the Super Admin denial lives in one place.
- UUID primary keys. All timestamps are `timestamptz` in UTC. Tenant and site keep an IANA timezone for display and shift-boundary maths (overnight shifts supported).
- State changes (shift open/close, acknowledge, escalate, resolve, verify) go **only** through RPC functions. They are idempotent (client request id) and write an AuditEvent in the same transaction.
- Ownership, acknowledgement and audit tables are append-only, enforced by revoking UPDATE/DELETE and by triggers.
- **Photos / attachments (07):** private bucket `attachments` (5 MB, jpeg/png/webp; checked nightly), path `tenant/<tenant_id>/<entity>/<id>/<attachment_id>.<ext>`. Two-phase upload: `*_attachment_begin` creates a pending row → client uploads (Storage INSERT policy allows only the caller's own pending path < 10 min old) → `*_attachment_commit` checks size/MIME against Storage metadata and marks it ready (trigger allows only pending→ready). No UPDATE/DELETE for clients. Reads use the user's session (`storage.download`) so RLS is checked per request — **except** that hosted Storage's CDN may re-serve an object the same user already downloaded until their access token expires (≤ 1 h): accepted residual risk. MIME type and checksum are client-declared. Client compresses to ≤ 1600 px JPEG 0.7 (~300 KB; Free Storage = 1 GB).
- **`app_policy` schema** is the only home for client-executable helpers used inside Storage/RLS policies: every function there is stable, security definer, empty search_path, returns boolean and is referenced by a policy (test-enforced). It is not exposed by PostgREST. Everything else in `app` stays non-executable for clients (02's test 004).
- Accessibility: WCAG AA contrast, touch targets ≥ 48dp, status shown as a label and not by colour alone.
- Connectivity: [Assumed] reliable Wi-Fi/4G. Each form keeps a local draft and retries submission; there is no offline sync.
- **Read timeout and retry (screen-speed D1 + D3, owner 2026-11-19):** the Supabase client's `global.fetch` (`src/lib/fetch-retry.ts`) aborts an idempotent read that has no response after 4 s and retries it once; a second stall surfaces the normal network error. Retried: GET/HEAD to `rest/v1` (not `rpc`) and Storage object downloads, and POSTs to an explicit allowlist of read-only RPCs (`READ_RPCS`: `my_shift`, `shift_board`, `reading_state`, `reading_detail`, `today_board`, `handover_checklist`, `handover_alerts`, `issue_alerts`, `issue_detail`, `issue_list`, `pa_audit`, `pa_super_admins`, `pa_tenant_summaries`, `pa_tenant_unit_admins`). `handover_checklist` qualifies because its only write is the `handover_session` snapshot (`insert ... on conflict do nothing`), so a repeat is a no-op; a denied call may add one more `access.denied` audit row. **Default deny:** every other rpc (`pm_*`, `sh_*`, `iss_*`, `rd_*`, `ho_*`, `psvc_*`, `svc_*`, anything new) and every POST/PATCH/DELETE, Auth, Edge Function and Storage upload keeps the platform default and is never auto-retried. **A feature that adds a read RPC adds it to `READ_RPCS` only after checking it writes nothing.** A caller's own AbortSignal is honoured (no retry). Each retry is a Sentry breadcrumb only (path without query string, no user data).
- Web security headers come from the `expo-router` plugin `headers` in app.json (EAS Hosting applies them for static/server output): CSP `default-src 'self'`, `script-src 'self'` + sha256 of Expo's single inline hydration script, `style-src 'unsafe-inline'` (react-native-web), `connect-src` Supabase + Sentry, `frame-ancestors 'none'`; nosniff; Referrer-Policy; Permissions-Policy; HSTS (EAS default). EAS converts X-Frame-Options into `frame-ancestors`. An Expo upgrade that changes the hydration script breaks the hash → caught by the smoke console-error check.
- Identity: one tenant per user in MVP (`membership.user_id` unique). Platform Super Admin is not a tenant member (separate model, feature 03).
- **Sign-in = phone number + password.** The Auth user's email is the non-deliverable `<10 digits>@phone.mouldtrack.invalid` (RFC 2606); the real phone (Indian mobile, unique platform-wide), name and employee ID (unique per tenant) live on `membership`. Temporary passwords: 12 chars, CSPRNG, shown once to the UA, 24 h expiry, forced change at first sign-in. Password policy ≥ 10 chars with letters + digits (enforced by the `account` function, mirrored in hosted Auth settings). When SMS arrives, the real phone can be added to the Auth user without changing accounts.
- **Audit:** `audit_event` is append-only (UPDATE/DELETE/TRUNCATE revoked from every role incl. service_role, plus a trigger). Phones are stored masked (`+91******1234`); passwords never appear in audit, logs or Sentry (Sentry scrubs phone/password/name/employee-ID keys and function request bodies).

## External integrations
None in MVP. Notifications are in-app (R3). Push/email/WhatsApp come later. **Chosen providers for later:** email = AWS SES (as Supabase custom SMTP when the first email flow is needed); SMS = AWS End User Messaging SMS (needs DLT registration in India). The owner's Mac and the Claude workspace cannot reach Expo's servers, so every EAS command runs in GitHub Actions.

## Release & regression policy (every release)
Regression = the whole suite (unit, DB/RLS, web e2e, Android e2e). Tests accumulate and are never edited to pass.
1. **Every PR:** the full suite runs in CI, and a PR merges only when green. The PR carries the AC → test → result table. Target is about 10 min or less: lint/typecheck/unit/build, DB tests and e2e shards run as parallel jobs. Each DB/e2e job gets its **own ephemeral Supabase (`supabase start`) built only from migration files**, with no shared database and no secrets. A schema change that works only on dev fails PR CI; that is intended.
   - **Accepted exception (owner, 2026-11-13):** Android Maestro e2e runs **only nightly and at the release gate, not on PRs**. PRs still compile the Android build (`npm run build`). Risk: a bug specific to native rendering can reach main and is caught at the next nightly. Mitigation: all workflow logic sits in the shared TS + RPC layer that the web e2e covers on every PR; a red nightly is the top priority the next day.
2. **Nightly** (`regression.yml`, 02:30 IST): full suite against dev incl. Android Maestro on an API 34 emulator; failure opens/updates a GitHub issue "Nightly regression failing" for the owner. Shared-DB isolation: N = 1 lane — one run per target (concurrency group); PR CI never touches hosted databases; fixtures reset by `scripts/fixtures-reset.ts` (refuses anything but local/dev). It also covers what PR CI can't: (a) dev has every migration (apply, then diff the live schema against the files); (b) dashboard and query speed on a seeded volume tenant (e.g. 200 machines × 90 days); (c) hosted-only behaviour (Auth settings, Storage policies, EAS Update channel reachable).
   - **Dev is rebuilt before every dev run (dev-reset chore, 2026-11-18).** Append-only history can't be deleted, so growth is stopped by rebuilding instead of cleaning: the `reset` job runs `scripts/dev-reset.ts` **after `drift` and before `web`, `android` and `hosted-checks`** (drift still proves deploy-dev's incremental apply on the un-reset database; staging and prod never get the job, and the script refuses anything but the local stack or the exact dev project ref, or any dev database holding a non-fixture phone). It empties Storage bucket `attachments`, runs `supabase db reset --remote=<db url> --no-seed --yes` (the migration files only; `--db-url` is its deprecated spelling), removes every Auth user through the Auth admin API, then runs `fixtures:reset` and the demo seed (`scripts/dev-demo-seed.ts`, past-dated rows inserted by the service role like the 06/07 fixtures; no trigger is disabled and no bypass exists in the schema). `scripts/dev-size-check.ts` then asserts the exact one-run baseline (counts per table, Auth users, Storage objects, computed from the fixture lists and the demo specification) and fails the run on any difference, so growth cannot return silently. `deploy-dev` and the dev regression share concurrency group `dev-db` (one writer at a time). A deploy triggered by a merge during a nightly queues behind it, but GitHub keeps only one pending run per group (a newer pending deploy replaces an older one), so the regression's last job `redeploy` (dev only, `actions: write`) dispatches `deploy-dev` on main whenever the newest successful deploy-dev run is not main's head; a scheduled run that fails or is cancelled opens/updates the "Nightly regression failing" issue (a run cancelled while still pending starts no job, so it cannot notify). A hosted proof on a feature branch rebuilds dev from the **branch's** migrations; the next nightly rebuilds it from main's (drift may be red on the first nightly after an unmerged proof). `deploy-dev` itself checks `supabase migration list` first: if dev holds a version main lacks (an unmerged proof), it runs `npm run dev:reset` before `db push`, so a merge never fails on remote-only migrations. After the reset the `reset` job also asserts bounds on `auth.audit_log_entries` and the database size (`scripts/dev-bounds.sql`), and the size check fails when the API exposes a public table or view that is neither counted nor in `IGNORED_RELATIONS` (so a new table such as 08's must be counted); `dev-reset` clears `auth.audit_log_entries` at its end (dev and local only). PR CI proves the whole reset on its own ephemeral stack: job `reset-roundtrip` (fixtures, demo, throwaway Auth user / Storage object / issue / reading, size check must fail, `dev-reset` in local mode, exact baseline, second round with identical counts, `scripts/demo-checks.sql`: every seeded summary equals `app._rd_compute_summary`, issue verification eligibility, RLS isolation of the demo tenant).
   - **Docs-only skip:** PRs or pushes touching only `sdlc/**` or `*.md` run a "what changed" job and skip the suites. A code PR's last commit before merge must have a full green run. Release evidence cites a code commit's green run only.
3. **Every release (R1, R2 …), gate before prod:** (a) main green · (b) regression passes against **staging** (web URL + staging EAS channel build) · (c) manual checklist signed off on staging, including one real Android device · (d) owner approval. After the prod deploy: **smoke tests only**, read-only. Data-writing tests never run against prod.
4. **Evidence:** every CI or regression run uploads JUnit XML, Playwright JSON/HTML and Maestro reports, kept ≥ 90 days. Each release commits `sdlc/releases/<Rn>.md` and copies the summaries to `sdlc/releases/<Rn>/evidence/`.

Release sign-off: Sidambara Raja · Evidence retention: 90 days · Regulated data never in fixtures: real names/phone numbers of plant staff, real customer production data. Fixture Auth addresses use `@phone.mouldtrack.invalid` (never deliverable); fixture phones use `+91 90000 00001–00099` (canonical) and `+91 90000 10000–99999` (throwaway, created by tests and removed by `fixtures-reset`); names are invented. Mutating tests run in their own fixture tenant (`e2e org U`). Local/CI Supabase ports live in 15320–15329, below the Linux ephemeral range, so `supabase start` never races outgoing connections for a port.

## Known debt & fragile areas
- **Synthetic Auth identity (02):** sign-in uses `<10 digits>@phone.mouldtrack.invalid` as the Auth email. It never receives mail; when SMS/OTP or email arrives (roadmap "Later") the mapping is replaced by a real phone/email identity and a data migration.
- **Users search has no index (02):** the Users list filters with `ilike` on name, employee ID and phone. Fine up to about 500 users per tenant; add a trigram index when a tenant approaches that.
- **Clock-window test skips (05):** 3 pgTAP cases skip explicitly inside narrow plant-time windows because write RPCs use `now()`; daytime CI and the 02:30 IST nightly cover the complementary windows.
- **UA alerts are web-only (07):** a 05 test pins "UA Home makes no RPC call" on native; UAs use web (tablet browser) in R1.
- **Platform audit throttling (03):** refused `platform-setup` calls are audited at most once a minute while a token is configured, and not at all when none is configured (by design: no DB writes for anonymous callers).
- **Staging hosted checks (02, R4):** the nightly `hosted-checks` job runs the Auth config check on staging only; the Edge Function, orphan, consistency and CORS checks are dev-only. The staging `auth-config.mjs --apply` and a first full staging run happen at the R1 release gate, so AC-15 for staging is proven there, not in feature 02.
- **Readings live on their own `/readings` screen (06):** the owner chose a separate screen for R1. 05's Home test was re-scoped in PR #20, so readings can move onto My shift after R1, and 08 may add a Home call.
- **Reading photos share 07's CDN residual risk (06):** an already-downloaded reading photo can be re-served for up to the access-token lifetime after access is removed (same accepted risk as issue photos).
- **`pa_audit` paging in 022 (06):** test 30 reads 10 pages of 50; more than about 480 client RPCs would need a wider bound. Each new client RPC adds one denial row.
- **Capture metric not reported yet (06):** `app.reading_capture` is tested but has no screen until 09; Today shows per-occurrence on-time counts only.
- **Seeded-volume speed check not built (dev-reset D8):** policy item 2(b) (dashboard and query speed on a seeded volume tenant, e.g. 200 machines × 90 days) is not implemented in the nightly; the demo tenant is a manual-testing aid, not a volume test. Waived for R1 (owner, 2026-11-26: pilot = 10 machines); build it before tenant 2 is onboarded or before R2, whichever comes first.
- **Hosted dev is rewritten every dev run (dev-reset):** a failed or interrupted reset leaves dev half-built until the next run (`dev-reset` is safe to re-run; it refuses non-fixture identities). The staging reset is not built: staging holds fixtures only and is rebuilt by hand at a release gate if needed.
- **Cover-stale handover has no e2e (08):** "a cover after the handover makes the earlier declaration stale" is proven by pgTAP 061/062 only; a clock-independent e2e would have to record a cover inside the running occurrence.
- **Handover alerts are not on the Issues alerts tab (08):** they are a separate card on UA Home (D10) so 07's pinned rpc tests stay untouched; spec AC-9 said "Home/Issues". Web only, like 07's alerts.
- **Privilege contract covers three schemas (explicit-grants):** `public`, `app`, `app_policy` only. `storage` and `auth` privileges are Supabase-managed and not asserted; a migration that adds a schema or a grant elsewhere must extend the scope of `070`. The expected list was taken from a local stack with the old defaults; hosted dev (old defaults) and staging/prod (new) are proven by the staging regression, not by pgTAP. `public.tenant` and `public.membership` keep the full table privilege set for `service_role` (TRUNCATE, TRIGGER, REFERENCES, MAINTAIN) as the old defaults gave it: parity kept, narrowing is a later hardening step.
- **R1 staging gate - OPEN (08):** staging's fixture tenants will be created through the Console and so will be **enforced**; 06's e2e openings (and any flow that records a supervisor opening) will hit `handover_pending` there. Opus decides the fix before the R1 release (options: a fixture-only way to create ungated tenants, e2e that declares first, or a staging reset script that sets `required = false` for the fixture tenants).
- **No Sentry source maps for EAS builds (R1):** `eas.json` sets `SENTRY_DISABLE_AUTO_UPLOAD=true` for preview and production (the Sentry Gradle step failed both staging APK builds without `SENTRY_AUTH_TOKEN`). Crashes are still reported, with minified stack traces. Fix: add a Sentry auth token as an EAS secret and drop the flag, before or soon after the prod pilot.
- **Playwright/Maestro cover readings without a photo on Android (06):** the photo path is proven by API and web e2e and on a real device at the R1 gate (as for 07).
